# Phone-first Assurance

The requested experience starts with an inbound call to Assurance, followed by a text link to the account dashboard when a document is needed. The user signs in with a phone verification code, reviews the caller-reported intake, and uploads fictional demo documents. Document-validation and extraction failures create a portal notification and queue a generic problem text. No case details or medical information belong in SMS.

## Implementation and identity

`backend/phone-worker.ts` is a separate Neon Function for AgentPhone webhooks and phone authentication. `backend/phone-auth.ts` uses pinned Better Auth 1.7.18 with its phone-number, bearer-session, and JWT plugins. Managed Neon Auth remains the existing email identity service; no managed users or passwords are migrated. Neon Managed Auth supports linking a number to an existing user but does not support phone-first signup, so the additional self-managed path is required for new callers. Official references: https://neon.com/docs/auth/guides/plugins/phone-number and https://better-auth.com/docs/plugins/phone-number.

`backend/phone-schema.ts` defines isolated phone auth, intake, preference, event, and notification tables. Migrations 0021 and 0022 add them. `drizzle.config.ts` includes both application and phone schemas. Better Auth creates accounts only after successful OTP verification. OTPs expire after five minutes and allow three wrong attempts. Requests have database-backed limits, including three OTP requests per phone per five minutes. No real password or email is requested for a new phone account; the internal `.invalid` email is not a deliverable address.

`backend/request-identity.ts` accepts only the fixed managed issuer or configured phone issuer. Phone JWTs require the assurance-cases audience and EdDSA signature, and start with a separate phone subject namespace. It checks the verified phone user in the database before resolving its account owner. A caller ID or webhook cannot authenticate an account.

Existing account holders can verify a phone in the dashboard and link it using both their existing account token and the new verified-phone token. Linking cannot reassign a number already attached to another owner, attach two phone identities to one existing account, or silently merge a phone account that already contains cases. After linking, phone login resolves to the original case owner ID. `src/phone-session.ts` keeps the phone bearer session in sessionStorage, exchanges it for short-lived API JWTs, and does not silently switch to another email account when a phone session expires. As with existing JWT authentication, a previously issued JWT can remain usable until expiry; phone API JWTs expire after five minutes.

## Inbound calls and portal requests

`backend/phone-intake.ts` handles a short structured intake: explicit text consent, workplace-injury versus health-insurance path, fictional narrative, then portal link. It stores a pending intake for 24 hours. It does not read private case details based on caller ID. The account owner must verify the matching number and explicitly confirm the intake before a case is created; repeated confirmation reuses that case. The narrative remains caller-reported information and does not authorize insurer outreach.

Raw AgentPhone webhook bytes are verified with the documented timestamped HMAC signature and five-minute replay window. Delivery ID plus payload hash prevents duplicate state changes and rejects conflicting reuse. Expected agent and number IDs are checked. Signed outbound events are ignored. This is webhook voice mode, not SIP and not Twilio. Configuration is prepared by `scripts/configure-inbound-phone.ts`; default invocation is a read-only plan. `--apply` requires SMS readiness and the enabled feature before changing the existing agent's inbound routing. It retains a private previous-agent snapshot and makes no call or message.

`request_document` is an additional case tool in `backend/case-tools.ts`, implemented by `backend/phone-document-request.ts`. It queues a fixed document-type request only for the verified case owner with active standing authority and separate case-text consent. It accepts no arbitrary address or message. One case/document type is deduplicated. New pinned case-agent versions include permission for it; previously pinned sessions are not silently changed. Queued and provider-accepted messages are not claimed as delivered.

## Documents and notification handling

`backend/document-routes.ts` queues a problem notice when upload validation fails. With the phone feature enabled, a local PDF text check identifies unreadable/scanned PDFs and size/page limits after storage. `backend/document-extraction-routes.ts` queues notices for known source-reading failures, failed/cancelled readers, and unverifiable output. These checks do not establish clinical correctness or guarantee that every document problem will be detected. An issue can only be messaged after it is detected; remote extraction currently still uses its existing authorized operator workflow and status refresh.

`backend/phone-messaging.ts` maintains the notification outbox. Known document failures attempt dispatch immediately; queued document requests are drained by the signed phone-notifications scheduler every minute. Only a consenting account/first-call intake, an explicitly allowlisted recipient, an enabled feature, and an SMS-ready AgentPhone number can send. A number-level database advisory lock serializes notification counts. Limits are six case notifications per recipient per day and thirty total per day; OTPs have their own request limits. A process interrupted after reservation leaves dispatching for reconciliation. Timeout/ambiguous sends become unknown and are never automatically repeated. Definite rejections or disabled delivery become held; enabling SMS does not silently resend held messages. Reply STOP clears case-text consent and cancels queued texts. Provider acceptance is stored separately from delivery verification.

Portal URLs use assurance.claims and require sign-in; the link itself grants no access. `src/PhoneSignIn.tsx` supplies OTP signup/sign-in and existing-account linking. `src/PhoneIntakes.tsx` presents intake review, case-text consent, and document notices inside the existing dashboard. `public/phone-opt-in.png` is a screenshot of the implemented OTP consent screen with a fictional number, published for carrier registration review. It contains no participant details.

## Configuration, rollout, and current gate

- PHONE_FLOW_ENABLED defaults false.
- PHONE_AUTH_BASE_URL is the public phone Function origin.
- PHONE_AUTH_SECRET and AGENTPHONE_WEBHOOK_SECRET are private generated secrets, scoped to the phone Function. The case API receives the public issuer only.
- PHONE_ALLOWED_NUMBERS is a comma-separated list of consenting demo recipients. Empty means no texts.
- Existing AGENTPHONE_API_KEY, AGENTPHONE_AGENT_ID, and AGENTPHONE_NUMBER_ID remain private server configuration.

The verified existing AgentPhone number returned outboundSms=registration_required; registration status was none. The user chose individual/no-EIN registration and supplied contact details privately. A complete registration draft is in ignored test-results/agentphone-registration-draft.json, never in this documentation. It targets the existing account rather than creating an unrelated sub-account. The provider lists a $25 individual registration charge; submission and carrier approval do not themselves prove this number is SMS-ready. No registration fee, number purchase, outbound call, or SMS has been authorized by this implementation. The number's current hosted inbound behavior is preserved until configuration is explicitly activated.

Verification commands: `npm run build`; `OUTREACH_TEST_DATABASE_URL=... npx tsx --test --test-concurrency=1 scripts/phone-flow.test.ts` against a disposable branch; `npx tsx scripts/phone-ui-check.ts` against the local preview. Tests capture synthetic OTPs and mock SMS/auth transport; they do not send texts. Live registration, number activation, inbound routing, and real call → text → OTP → upload verification remain required before advertising phone-first availability.

Deployment preparation: the nine phone integration tests, thirty-five session/approval regressions, ten MCP/configuration tests, browser OTP fixture, and build passed. Production migrations 0021–0022 are applied and seven Functions are deployed with PHONE_FLOW_ENABLED=false and an empty recipient allowlist. Existing inbound hosted mode is unchanged. Existing agent-spending/operator restrictions still apply to phone accounts; phone verification alone never grants agent spending. Live carrier delivery and call routing are not yet verified.
