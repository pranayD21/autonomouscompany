# Phone-first Assurance

The live SMS feature currently verifies phone sign-in through Twilio Verify. It does not yet deliver upload links, document requests, or case updates. The intended call-first experience is: call Assurance, describe the issue once, receive a secure upload link, verify the phone, and let the agent continue from the saved account. AgentPhone handles voice and those case texts; its carrier registration is still pending, so this separate flow remains disabled. No case details or medical information belong in SMS.

## Current phone-login configuration

Phone login is separate from inbound voice intake and case notifications. `PHONE_LOGIN_ENABLED=true` enables phone authentication, phone JWT acceptance, and authenticated `/phone/*` routes. `PHONE_FLOW_ENABLED=true` also implies login, but remains the independent gate for inbound AgentPhone webhooks and case-notification sends. Enabling login does not activate inbound routing or case texts.

`PHONE_SMS_PROVIDER=twilio_verify` selects Twilio Verify for real login codes; the default remains `agentphone`. Twilio configuration uses server-only `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, and `TWILIO_VERIFY_SERVICE_SID`. The auth instance fixes its provider when constructed. Sending starts a Verify SMS verification; checking submits the user's code and requires `approved`. A 404 check is an invalid/expired/used verification. A database nonce still enforces five-minute expiry, three wrong attempts, and single consumption, because Better Auth's custom verifier replaces its native OTP validation. Existing real-number request throttles remain in force. AgentPhone sign-in codes bypass only the optional case-notification recipient rollout list, not readiness or authentication abuse controls. New voice calls remain AgentPhone-only. Case notifications also remain on AgentPhone regardless of the login-code provider. `smsReady` checks AgentPhone notification readiness with the flow flag; `signInSmsReady` checks the selected login provider with the login flag.

`PHONE_TEST_NUMBERS` is a comma-separated list restricted in code to fictional `+1 NXX-555-01XX` numbers (N is 2–9). Other configured numbers are discarded. `PHONE_TEST_CODE` is a public six-digit code, default `123456`; these accounts are shared fictional demo identities, not proof of phone ownership. They must contain only fictional data. Code requests for these explicitly configured fictional numbers never reach either provider and are exempt from request throttling. Verification still requires a fresh expiring nonce and rejects replay. `sendPhoneText` refuses to send any SMS to these test numbers.

The public `/status` endpoint returns `enabled`, `smsReady`, `testNumbers`, and `testCode`. Test numbers/code are exposed only while login is enabled. Verify readiness is a read-only service lookup; it does not prove delivery to any recipient. Fictional test login works while real SMS readiness is false. This implementation introduces no schema migration. Relevant provider contracts: [Twilio Verifications](https://www.twilio.com/docs/verify/api/verification) and [Verification Check](https://www.twilio.com/docs/verify/api/verification-check).

## Implementation and identity

`backend/phone-worker.ts` is a separate Neon Function for AgentPhone webhooks and phone authentication. `backend/phone-auth.ts` uses pinned Better Auth 1.7.18 with its phone-number, bearer-session, and JWT plugins. Managed Neon Auth remains the existing email identity service; no managed users or passwords are migrated. Neon Managed Auth supports linking a number to an existing user but does not support phone-first signup, so the additional self-managed path is required for new callers. Official references: https://neon.com/docs/auth/guides/plugins/phone-number and https://better-auth.com/docs/plugins/phone-number.

`backend/phone-schema.ts` defines isolated phone auth, intake, preference, event, and notification tables. Migrations 0021 and 0022 add them. `drizzle.config.ts` includes both application and phone schemas. Better Auth creates accounts only after successful OTP verification. OTPs expire after five minutes and allow three wrong attempts. Requests have database-backed limits, including three OTP requests per phone per five minutes. No real password or email is requested for a new phone account; the internal `.invalid` email is not a deliverable address.

`backend/request-identity.ts` accepts only the fixed managed issuer or configured phone issuer. Phone JWTs require the assurance-cases audience and EdDSA signature, and start with a separate phone subject namespace. It checks the verified phone user in the database before resolving its account owner. A caller ID or webhook cannot authenticate an account.

Existing account holders can verify a phone in the dashboard and link it using both their existing account token and the new verified-phone token. Linking cannot reassign a number already attached to another owner, attach two phone identities to one existing account, or silently merge a phone account that already contains cases. After linking, phone login resolves to the original case owner ID. `src/phone-session.ts` keeps the phone bearer session in sessionStorage, exchanges it for short-lived API JWTs, and does not silently switch to another email account when a phone session expires. As with existing JWT authentication, a previously issued JWT can remain usable until expiry; phone API JWTs expire after five minutes.

## Inbound calls and portal requests

`backend/phone-intake.ts` handles a short structured intake: an explanation of case assistance and text consent, workplace-injury versus health-insurance path, the caller’s account, then an upload link. It stores a pending intake for 24 hours. It does not read private case details or start work based on caller ID. The verified owner can submit the intake with `POST /phone/intakes/:id/claim`, `{confirm:true,start_agent:true}`. This creates the case, recorded standard intake scope, authority-bound credential, and direct run atomically. If activation is unavailable, the entire claim transaction rolls back and the call intake remains available to retry. Historical claim requests without `start_agent:true` still only save a case; retrying a claimed intake returns its original case and never starts or restarts permission.

Raw AgentPhone webhook bytes are verified with the documented timestamped HMAC signature and five-minute replay window. Delivery ID plus payload hash prevents duplicate state changes and rejects conflicting reuse. Expected agent and number IDs are checked. Signed outbound events are ignored. This is webhook voice mode, not SIP and not Twilio. Configuration is prepared by `scripts/configure-inbound-phone.ts`; default invocation is a read-only plan. `--apply` requires SMS readiness and the enabled feature before changing the existing agent's inbound routing. It retains a private previous-agent snapshot and makes no call or message.

`request_document` is an additional case tool in `backend/case-tools.ts`, implemented by `backend/phone-document-request.ts`. It queues a fixed document-type request only for the verified case owner with active standing authority and separate case-text consent. It accepts no arbitrary address or message. One case/document type is deduplicated. New version-2 owner permissions are accepted without requiring the historical synthetic/expiry policy; owner matching, active authority and separate text consent still apply. New pinned case-agent versions include permission for it; previously pinned sessions are not silently changed. Queued and provider-accepted messages are not claimed as delivered.

## Documents and notification handling

`backend/document-routes.ts` queues a problem notice when upload validation fails. With the phone feature enabled, a local PDF text check identifies unreadable/scanned PDFs and size/page limits after storage. `backend/document-extraction-routes.ts` queues notices for known source-reading failures, failed/cancelled readers, and unverifiable output. These checks do not establish clinical correctness or guarantee that every document problem will be detected. An issue can only be messaged after it is detected; remote extraction currently still uses its existing authorized operator workflow and status refresh.

`backend/phone-messaging.ts` maintains the notification outbox. Known document failures attempt dispatch immediately; queued document requests are drained by the signed phone-notifications scheduler every minute. Only a consenting account/first-call intake, an enabled feature, and an SMS-ready AgentPhone number can send. PHONE_ALLOWED_NUMBERS is an optional rollout restriction: a populated list restricts recipients, while an empty list permits the otherwise-authorized recipients. The former six-per-recipient and thirty-total case-notification caps are removed under the current autonomy instruction. Number-level and row locks preserve dispatch exclusion; OTP request and verification abuse controls remain separate. A process interrupted after reservation leaves dispatching for reconciliation. Timeout/ambiguous sends become unknown and are never automatically repeated. Definite rejections or disabled delivery become held; enabling SMS does not silently resend held messages. Reply STOP clears case-text consent and cancels queued texts. Provider acceptance is stored separately from delivery verification.

Portal URLs use assurance.claims and require sign-in; the link itself grants no access. `src/PhoneSignIn.tsx` supplies OTP signup/sign-in and existing-account linking. `src/PhoneIntakes.tsx` presents intake review, case-text consent, and document notices inside the existing dashboard. `public/phone-opt-in.png` is a screenshot of the implemented OTP consent screen with a fictional number, published for carrier registration review. It contains no participant details.
