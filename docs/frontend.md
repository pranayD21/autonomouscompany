# Frontend workspace

The browser app is a React/Vite single page (`src/`). Signed-out visitors see the landing page (`src/Landing.tsx`); signed-in users get the case workspace (`src/Workspace.tsx`). Styling is plain CSS in `src/style.css` and `src/landing.css`; animation uses the `motion` package. Several components are adapted from Aceternity UI (MIT): the hover-expand sidebar (`src/ui/Sidebar.tsx`), the upload pill (`src/ui/FileDrop.tsx`, a shrunk file-upload drop zone) and the number ticker (`src/ui/motion.tsx`).

## Mobile layout

`src/mobile.css` is imported last by `src/main.tsx` and contains only `max-width: 820px` and `max-width: 480px` overrides. The existing desktop styles in `src/style.css`, `src/landing.css`, and `src/overview.css` are unchanged. The 820px boundary matches the existing workspace navigation breakpoint; narrower phones receive additional spacing and full-width primary actions at 480px.

On the landing page, the hero CTA reads **Tell us what happened** on every screen size (it was **Open a case**). At 820px and below the landing hero stacks wordmark, headline, a mobile-only line (“Start with your phone number. We’ll call you and take it from there.”), a full-width CTA and a mobile-only “See how it works” link; the header hides “How it works”, the CTA drops its looping shimmer animations, and the steps and footer tighten. `.landing-mobile-only` elements are hidden by default in `src/landing.css` and shown only inside the mobile media query. The header plus hero fill exactly one screen (`min-height: calc(100svh - var(--header-h))` on `.minimal-root`, set by `useBackdropLayout` in `src/Landing.tsx`), and the hero content is a flex column with `justify-content: space-between`, so the wordmark, headline and CTA spread evenly and “See how it works” (with a small nudging arrow) sits at the bottom of the first screen. Below the fold, the three steps are rounded cards with circular number badges, with wider section and footer spacing.

The overrides cover the landing header, hero CTA, explanatory steps and credits; phone/email entry and case-intake fields; overview cards, filters and case rows; case status, activity, outcomes, evidence and document uploads; and the shared conversation composer. Inputs use 16px text to avoid focus zoom on mobile browsers, primary controls provide at least 44px touch targets, long identifiers and text can wrap, and forms collapse to a single column. The conversation log has a viewport-aware height. Safe-area padding and small/dynamic viewport units accommodate device edges and browser chrome without disabling pinch zoom or hiding page overflow.

The mobile drawer in `src/ui/Sidebar.tsx` exposes a named modal dialog, moves focus inside on open, cycles Tab/Shift+Tab within its links and buttons, closes on Escape or hash navigation, restores focus to the trigger when available, and restores the previous body scroll setting on close/unmount. Resizing to desktop clears the sheet; the desktop hover rail is unchanged. Drawer contents scroll independently, with space for the close and sign-out controls.

Verification: run `npm run build` with the normal three public `VITE_*` service URLs, and `npx tsx --test scripts/claim-composer.test.tsx scripts/progress.test.ts scripts/activation-state.test.ts`. On November 8, 2026, TypeScript/Vite and all 15 focused tests passed using non-production placeholder public service URLs for the build. A PostCSS AST check confirmed all 110 new style rules are enclosed by the two mobile-only queries. Browser/device layout and keyboard checks have not been run for this change. Before release, check 320/390/480/768/820px widths, landscape, long filenames/case titles, open details, the software keyboard and drawer focus/scroll behavior, then compare desktop at 821px and wider against the existing design. The isolated UI fixture scripts that import only `src/style.css` do not automatically include the new app-entry stylesheet; include `src/mobile.css` when using those fixtures for mobile acceptance.

### iPhone audit (2026-11-08)

The user asked for a full mobile audit on an iPhone. Xcode's iOS Simulator is not installed on the development Mac, so the audit uses Playwright's WebKit engine (Safari's) with the built-in `iPhone 15`, `iPhone SE` and `iPhone 15 landscape` device profiles. These set touch, pixel ratio and the mobile Safari user agent. `scripts/mobile-audit/` serves the real app through `vite.config.ts` on port 4290, with `@neon/realtime-react` swapped for `mock-realtime.tsx`. `audit.ts` mocks every phone-auth and cases API call with fictional data. It captures landing, sign-in, the code step, the overview, the drawer, a case chat (typing, Case info sheet, resolved, empty, new) and the new-case page. On each screen it records horizontal overflow, tap targets under 44pt, inputs under 16px, and text under 12px. Run it with:

```
npx playwright install webkit
VITE_CASES_API_URL=https://mock-cases.compute.example.com VITE_NEON_AUTH_URL=https://mock-auth.example.com/auth VITE_NEON_REALTIME_URL=wss://mock-rt.example.com npx vite --config scripts/mobile-audit/vite.config.ts &
DEVICE="iPhone SE" OUT=test-results/mobile-audit npx tsx scripts/mobile-audit/audit.ts
```

Fixes from that audit:

- **Safe areas.** `index.html` now has `viewport-fit=cover`. Without it, every `env(safe-area-inset-*)` resolved to 0. The landing and sign-in headers and footers gained insets. `.mobile-bar` is `64px + env(safe-area-inset-top)`, and the case page and `.surface` heights subtract that inset. `theme-color` (#f5f4ef), `apple-mobile-web-app-title` and `public/apple-touch-icon.png` were added. `public/manifest.webmanifest` (`display: standalone`) and the `apple-mobile-web-app-capable` meta let the site be installed from Safari's Share → Add to Home Screen and open full-screen, without browser bars. There is no service worker or offline mode; the installed app loads the live site.
- **Error boundary.** `src/ErrorBoundary.tsx` (with `src/error-boundary.css`) wraps `<App/>`. A render error shows a reload card instead of a blank page. `Documents` guards `extraction_result.uncertainties`.
- **Case page.** At 820px and below the case header is about 57px, with 44px round buttons and a one-line title and status. A short-landscape query (`max-height: 500px`) tightens the header and composer so messages stay visible. Send, the bubble action, the start banner button, Edit, the sheet summaries and the document buttons are all at least 44px. On phones, Case info is a fixed bottom sheet: it dims the whole screen including the app bar, has 22px top corners and a grab handle, and is at most 88dvh tall. When the conversation state has no label of its own, the header shows the overview's `deriveProgress` wording (`fallbackStatus`), not "Your case conversation". The document chip reads "Read by Assurance" with a check, in plain status styling. `.facts dd` no longer capitalises user data.
- **Names.** `src/format.ts` has `formatPhone` and `isPersonName`. Phone-only accounts show "(415) 555-0123" rather than E.164. `isPersonName` rejects phone numbers, email addresses, any name containing the word "Assurance" (phone sign-up stores the placeholder "Assurance caller", which once produced "Good morning, Assurance") and generic placeholders such as "Your account", "Caller" or "User". `main.tsx` only passes the stored name to the workspace when `isPersonName` accepts it; otherwise the drawer shows the formatted phone number (or email). The greeting is just "Good morning" when there is no real name, and the drawer avatar shows a person icon instead of "+".
- **Onboarding notice.** It is one flat card. **Open your case** is a blue 44px pill, and the stop action is a quieter text button below it.
- **Overview and drawer text.** Labels are at least 12px and the filter pills and legend 13px. The filter bar scrolls inside itself below 640px. Between 360 and 480px the bento is a compact two-column grid. The drawer section label and case initials are 12px, with a status ring on each case initial.
- **Sign-in.** The code hint sits between the label and the input and is linked with `aria-describedby`. The code field autofocuses and has a "6-digit code" placeholder. The sent number shows formatted. The fine print is 13px on phones.
- **Landing.** "Open workspace" is 13px. The footer and photo credit are 12px, and the credit links are about 36px tall. The step cards are tighter. A `max-width: 1000px and max-height: 500px` query caps the wordmark at `min(17.1vw, 22svh)`, so the CTA is visible in landscape.

## Hash navigation

On phones (`(max-width: 820px), (pointer: coarse)`), in-app navigation replaces the current history entry instead of pushing one (`src/mobile-nav.ts`: `goToHash`, and `installPhoneHashNavigation` in `main.tsx`, which routes same-page `<a href="#…">` route links and leaves in-page anchors, skip links, `target`/`download` links and modifier clicks alone). iOS Safari turns a swipe from the left edge into Back, which jumped to the previous screen (usually the overview) when people were trying to open the menu. Sign-in and intake redirects use `location.replace` too. `src/ui/Sidebar.tsx` adds the menu gestures: a swipe right that starts within 28px of the left edge opens the drawer, and a swipe left on the open drawer closes it. Both ignore horizontal scrollers, form controls, text selection, mostly-vertical moves, multi-touch, and an open Case info sheet. Desktop keeps normal Back behaviour. `scripts/mobile-nav-ui-check.ts` checks all of this in WebKit with fictional data (it needs the `scripts/mobile-audit` server on port 4290). A tab whose history already holds earlier app screens can still go back once, until the next replace.

Hash routes keep the open view across reloads: `#home` (landing), `#workspace` (overview), `#new` (intake form), `#case/<id>` (one case). While the session check is pending, `#home` renders the landing page immediately and other non-workspace URLs render nothing (plain paper); only `#workspace` and `#case/...` show the "Loading your session…" shell. This stops the shell's header and footer divider lines flashing before the landing page.

## Workspace layout

The workspace keeps only what the case workflow needs. Each screen answers three questions in order: what is happening, does it need me, and what has been done.

**Overview** (`src/Overview.tsx`, styles in `src/overview.css`; re-exported from `src/Workspace.tsx` for fixtures). It matches the landing page palette. Top to bottom:

- Header: time-of-day greeting (no name when the account has only a phone number or email), a large tight "Your cases." heading with the blue wordmark period, and the landing-style **Open a case** pill (ink with a blue arrow circle that turns 45° on hover). The summary sentence under the heading was removed at the user's request (2026-11-08).
- Stats card (`.ov-stats`): one plain white card with a rule border, styled like the case rows, split into **Needs you** (amber, and a link to the first case needing the owner when above zero), **In progress** (with the resolved count), and **Reported savings** (animated count-up; the sum of each case's latest outcome `reduction_cents`). Amounts drop the cents when they are whole dollars or at least $1,000 (`wholeDollars`); the case rows use the same rule. On phones (≤640px) Needs you and In progress share a row and Reported savings takes a full-width row beneath. This replaced the orange "Needs you" card, the dark hatched savings card and the "All cases" meter card, which the user found inconsistent with the rest of the UI.
- Case list: numbered rows (`01`, `02`… in blue monospace, like the landing "How it works" steps), sorted needs-you, waiting, resolved. Each shows case type and insurer/employer, title, the `deriveProgress` next step (amber when it needs the owner), the status badge, any reported savings, and an arrow circle that fills blue on hover. A sliding white hover highlight and a filter pill (All / Needs you / Waiting / Resolved, with counts) use `motion` layout animations. Filter hover colours apply only under `@media (hover: hover)`, and the selected label has a higher-specificity light colour, because iOS keeps a tapped button in `:hover` and the selected label used to turn ink on the ink pill. An empty filter shows a centred icon, a title and a line of help specific to that filter (`EMPTY` in `Overview.tsx`). Unloaded progress shows shimmer placeholders. **Open another case** closes the list.

Progress comes from `deriveProgress` in `src/progress.ts` via `useProgressMap`. `deriveProgress(case, snapshot, agentEnabled)` is pure and covered by `scripts/progress.test.ts`; its snapshot comes from `/documents`, `/crew`, `/actions`, `/replies`, `/outcomes` and `/autonomy`. It refreshes when a non-GET `/cases/:id/...` request succeeds (`src/services.ts` dispatches `assurance:case-changed`), on window focus, and every 30 seconds while the tab is visible. Pending phone intakes and the phone-link control (`src/PhoneIntakes.tsx`) appear only here, under the header.

**Case page** (`CaseView` in `src/Workspace.tsx`): since 2026-11-08 a full-page chat modelled on the user-supplied 21st.dev "AI Chat Card" (Arihant Jain). Only its layout was used, rebuilt in plain CSS in `src/claim-workspace.css`, with no Tailwind, lucide or typewriter demo. The user asked for this after the dark full-window header, and asked that a non-technical person see only what they need.

- **Frame.** The chat is the whole page, not a card. When a case is open, `.surface` loses its margin, border and radius and becomes a white, full-height column (`.surface:has(.claim-chat-page)`). Header, messages, banner and composer content sit in a centred 760px column (`--col`), with the header rule spanning the full width. At 820px and narrower it fills the screen below the mobile bar (`100dvh - 64px`). Messages scroll inside, and the composer stays at the bottom.
- **Header.** A round back button, the case title on one line with ellipsis, a plain status line with a coloured dot (from `CaseChat`'s conversation state: "Working on your case", "Waiting for your reply", "Getting started", "Paused", "Work finished"), and one round **Case info** button. It shows a blue dot once an outcome exists.
- **Messages.** Assistant bubbles are soft grey and owner bubbles ink. Author labels are visually hidden (screen readers still get them). A document request shows an **Add the document** pill that opens the file picker. With no messages, the empty state shows the logo tile (gently bobbing), "Let’s take it from here." and one line of help pointing to **Add documents**.
- **Start banner.** When work can start (`canStart` from `Autonomy`'s `render` parts), a pale-blue card above the composer explains it in one sentence with **Start handling my case**, or for a previously stopped case "Assurance is paused…" with **Start again**. The separate paused note is hidden while that banner shows.
- **Composer.** `ClaimComposer` restyled as a grey rounded box with the animated upload pill (`CaseDocumentUpload` → `src/ui/FileDrop.tsx`, labelled **Add documents** so its purpose is clear; the blue tile pops up out of a dashed outline on hover or drag and uploads immediately) and a round black send button. The keyboard hint and counter remain for screen readers and long messages, but the hint is visually hidden.
- **Case info sheet.** A dialog that slides in from the right on desktop and up from the bottom on phones. On phones it closes with a downward swipe that tracks the finger, starting from the grab handle, the header, or the body when every scrollable area under the finger is at the top (touch listeners in `CaseView`; a drag past 90px or a flick above 450px/s closes it, anything less springs back; the backdrop fades as it moves). It moves focus to its close button, closes on Escape or a backdrop click, and returns focus to the info button. Sections, in plain language: **Where things stand** (`ClaimProgress` stepper), **Result** (`Outcomes`, only when one exists), **Your documents** (`Documents bare`), **What we’ve done** (the day-grouped activity feed from `Autonomy`), **Your details** (description, facts with plain labels, Gmail for email accounts, **Edit**), and **Assurance’s work** (the `Autonomy` status section with Stop/Start, approvals and goal, then **Delete case**).
- **Theme.** Matches the website. The page, header, composer area and Case info sheet use the overview's surface colour (`--surface`, #fbfbf8), with `--rule` lines; Assurance bubbles are white cards with a rule border; owner bubbles are ink; round header buttons are white with a rule border and turn blue on hover; the empty-state title ends in a blue period like the wordmark; the composer is a white card that gets a soft blue focus ring; Send is the landing page's blue arrow circle (grey when empty). **Add documents** is one fully rounded paper pill with a round blue tile (blue-tinted on hover/drag) so it sits cleanly inside the composer.
- **Message layout.** Messages sit just above the composer when there are only a few (the log is a flex column whose first child has `margin-top: auto`). Day dividers ("Today", "Yesterday", or a date) separate days. Consecutive messages from the same sender within ten minutes are grouped, with a 4px gap, and only the last one shows a clock time (the full date is in the tooltip). Only messages that arrive after the page loads fade in.
- **Header button.** **Case info** is a labelled pill on wider screens and an icon-only round button at 640px and below.
- **Account notices.** The phone onboarding status (`OnboardingCallNotice` in `src/phone-onboarding.tsx`) shows on the overview and other workspace views, but not on case pages. It is a small pill pinned to the top right of the content: a status dot and two or three words from `callLabel` ("Call needed", "Call requested", "Opening case", "Case ready", "Onboarding stopped"), plus a chevron. No box, no paragraph. The dot is amber when the call needs the owner, blue while work is moving (with a soft pulse, off under reduced motion) and grey once stopped. Beside a short first line (the overview greeting, the **All cases** link) the pill takes no height; on pages that start with a heading (a first-run account with no cases) it keeps a 34px row so it never covers the heading (CSS `:has()` in `src/style.css`). The full status sentence is in a visually hidden `role=status` (or `role=alert` when the owner must act) region. Tapping the pill opens a popover with that sentence, the call-back instruction, **Call (412) …**, **Open your case** when one exists, the call transcript and **I don’t need this**. The popover takes focus, closes on Escape (focus returns to the pill) or an outside tap, and every control is at least 44px tall. **I don’t need this** asks inline first ("Stops the call follow-up and deletes this case. This can’t be undone." or, with no case, "Stops the call follow-up. Nothing else changes.") with **Delete case**/**Stop follow-up** and **Cancel**; Escape backs out of the confirmation. Only after confirming does it call `POST /phone/onboarding/stop` (skipped when already stopped) and then `DELETE /cases/:id` for the onboarding's `case_id`, then hides the pill and remembers that in `localStorage` (`assurance-onboarding-dismissed:<owner>:<status>`, wrapped in try/catch). A failed stop deletes nothing; a failed delete after a successful stop says so. Settled states also offer **Hide**. Stopping without deleting an open case stays available from that case's sheet. The **Call us to open it** card on `#new` uses a blue pill whose number stays white (the generic `.surface a` link colour skips `.primary-link`).
- **No save banner.** Sending a chat message no longer shows "Message saved."; the message appearing in the conversation is the confirmation. Failed sends still show an error with **Retry message**.
- **Plain waiting reasons.** `plainWaiting` in `src/progress.ts` turns an agent session's `waiting_on` note into customer words. Internal reasons (authority, credential, operator access, token, session, lease, budget, staffing, scheduler, engine, provider) become "Waiting on something on our side". Other notes read "Waiting on …". The stepper, overview and status strip all use it.
- **Removed from this page as not needed by a non-technical person:** the claim-number eyebrow, progress meter, panel tabs, the always-visible goal/scope text, the claim-stage fact, the keyboard hint, and the refresh button (messages poll every 5 seconds). Stop/revocation stays available in the sheet.

`CaseView` uses `useProgressMap([item])` (the overview's `deriveProgress`) for the stepper and the outcome dot. `Autonomy`'s `render` prop returns `status`, `activity`, `activityCount`, `working`, `canStart`, `started`, `start`, `busy` and `error`. `CaseChat` takes `title`, `headerStart`, `headerEnd`, `beforeCompose`, `pausedNote` and `children` (the overlay). The legacy `compact` layout of `Autonomy` and the disclosure form of `Documents` remain for other callers.

### Claim composer

Main-branch integration: the persistent conversation in `src/CaseChat.tsx` also uses this composer and blue orb. Its existing `/messages` API, server-backed history, polling, permission gate and stable retry payload remain intact. Pending uncertain messages keep the draft read-only while leaving the retry button available. Version-2 cases use that persistent conversation rather than a duplicate status-panel update box; older direct-model cases retain their existing `/updates` fallback. Each composer has unique label and hint IDs. On the case page the persistent chat uses an ink header, a cool tinted message area and solid-blue owner bubbles (changed 2026-11-08 at the user's request for more contrast).

`src/ui/ClaimComposer.tsx` adapts the rounded input and compact toolbar from the user-supplied 21st.dev prompt-box reference without its dark palette, global style injection, or simulated voice/search/think/canvas features. It uses React and the existing icons. Styles live in `src/style.css` and use the shared landing tokens from `src/landing.css`.

The controlled textarea grows up to 200 px and retains the 4,000-character API limit. Enter submits nonblank text; Shift + Enter inserts a newline, and IME composition does not submit. A labeled circular send button and saving indicator reflect the real owner-update request. Saving disables editing and submission. The persistent chat mounts the animated **Add files** picker inside the composer. Uploads run immediately, independently of sending text. The legacy composer's **Case documents** shortcut opens the document-library disclosure and focuses its summary. Existing upload validation, storage and extraction remain unchanged. The counter appears near the limit and keyboard instructions appear on focus. See [claim-chat-design.md](claim-chat-design.md).

`Autonomy` sends through the authenticated `POST /cases/:id/updates` endpoint, preserving its retry UUID and error handling. On successful saving, it displays the latest locally submitted update in a right-aligned bubble. This is a save receipt, not a generated agent answer or a complete conversation history. Saved updates remain in case notes after reload; the receipt bubble itself is not persisted. Processing follows the agent scheduler. Case-keyed mounting in `src/Workspace.tsx` resets drafts and receipts on navigation between claims.

Verify with `npx tsx --test scripts/claim-composer.test.tsx scripts/activation-state.test.ts scripts/progress.test.ts` and `npm run build` with the three public service URLs configured. The composer tests cover rendered labels, empty-message disabling, saving state, answer-mode copy and safe escaping; they do not exercise browser keyboard, scrolling, focus, or layout behavior.

Removed from the signed-in app, with the reason:

- The hardcoded "See what Assurance is doing for you" card was identical on every case, so it gave no information.
- The bill/EOB "potential discrepancy" card and the overview's "$ to investigate" total subtracted two numbers the user typed in, which is not a verified discrepancy and means nothing for workplace injury. The amounts remain in Details. Overview money comes only from agent-reported outcomes.
- The section tab bar and Done/Next-step tags. (The tabs were briefly restored, then removed again at the user's request.)
- "Case agent setup", "Scope and controls", engine name, finish condition, and "Round N" labels were internal. The engine label helper remains in `activation-state.ts` for tests.
- The legacy optional Naïve review and the manual draft-and-approve outreach form. Agent emails enable reply monitoring automatically (`backend/open-case-actions.ts`), and replies appear in Activity. The backend endpoints are unchanged, and no signed-in view mounts either control.
- The document-type dropdown (uploads use `kind: "other"`).
- The visible green live dot (a hidden "Live updates connected" label remains, and a visible pill appears only while reconnecting), the workspace footer, and the per-case status text in the sidebar.

`deriveProgress` does not tell the owner to "Approve your outreach draft". No approval control exists, and an agent email is briefly in `draft` while it sends.

## Brand mark and hero wordmark

The logo is a two-stroke "A" drawn as the `Logo` SVG component in `src/Icons.tsx`, filled with the brand blue (`--blue`, `#2465ef`). It appears in the landing header, the sign-in header and the workspace sidebar, nudged down `.09em` so it centres on the lowercase wordmark. `assets/icon.svg` (README) and `public/favicon.svg` use the same paths with no background.

The landing hero (`src/components/strikethrough-replace.tsx`, styles in `src/landing.css`) animates in two phases. First a line strikes through "in" and a handwritten blue "as" is written above it. Then the "as" drops into line, sitting `.1em` below the bottom of "surance" (canvas-measured ink bounds) so the script reads as part of the word, while the struck "in" slides down at full size behind the "Insurance is complicated." heading. A mask fades the "in" out before it reaches that heading (the `fadeBelow` prop names it). The mask's stops are offset by the registered `--in-y` property so the fade stays fixed on the page while the word moves. Offsets are measured in em and re-measured on font load and resize. Extra space under the wordmark (`.42em` bottom padding) sets the heading and call to action lower so more of the dropped "in" shows. With reduced motion the page shows the settled layout immediately.

## Hero photo backdrop

The backdrop component is `src/components/hero-backdrop.tsx`, rendered first inside `<main className="landing-page">` in `src/Landing.tsx`. It shows nine documentary photos of real people recovering from injuries: people on crutches, hand and leg therapy, a patient in a hospital lift, someone being helped into a wheelchair or down steps. One photo shows at a time; every 5 seconds a 0.45s crossfade switches to the next. It pauses while the tab is hidden, and with reduced motion only the first photo shows. Each photo has an `objectPosition` so the cover crop keeps the person in view. The layer is `aria-hidden`.

Its size depends on scroll position (`useBackdropLayout` in `Landing.tsx`, which measures the header and hero with a `ResizeObserver` into `--header-h` and `--hero-end`, and adds `is-at-top` to `<main>` while `scrollY < 8`):

- At the top of the page the photos cover at least the full viewport, behind the header, hero and anything else in view, with no top or bottom fade. The divider lines under the header and above "How it works" are hidden.
- Once the visitor scrolls, the layer shrinks to the header + hero area over 0.5s and `.hero-backdrop-fade` fades in: solid paper over the header, a fade in at the top of the hero, and a fade out over its bottom 30%. The divider lines come back.

Styles in `src/landing.css` (`.hero-backdrop*`) keep a little colour (`saturate(.35)`) at 42% opacity and wash the edges toward the paper colour so the wordmark and copy stay readable.

Files are `public/hero/01-*.webp` to `09-*.webp` (about 820 KB together, up to 1600px). Sources:

- Public domain (US Navy / Navy Medicine on Flickr and Wikimedia Commons): hand therapy (Flickr 52033349927), wheelchair help (Commons "US Navy 070919-N-6278K-182"), patient lift (Flickr 51929649462), leg rehab (Flickr 52971670817), helped down steps (Commons "US Navy 050413-N-1485H-010"), band therapy (Flickr 52257078214).
- Public domain mark on Flickr: crutches outdoors ("Duel Crutches", Belur Math, Howrah, 51633131050) and crutches in the city ("IMG_0037", evanizzle79, 54314915502).
- CC BY 2.0: crutches on a street in Chiapas by Adam Jones (Commons "Man on Crutches - San Cristobal de las Casas - Chiapas - Mexico.jpg"). The licence requires credit, which `src/Landing.tsx` gives in the footer (`.photo-credit`). Keep that credit while the photo is used.

## Copy and hierarchy rules

Two rounds of a persona-based design review set these rules (verdicts were kept outside the repository):

- The landing page has no FAQ/questions section. After the hero and "How it works" steps it goes straight to the footer.
- The landing keeps two signature lines, "Insurance is complicated. Getting help shouldn't be." and "You've got enough on your plate.", and drops other slogans.
- Relevant qualifications appear under money and AI output, and a concise scope disclosure accompanies submission. Repeated redundant status banners are removed.
- Money appears only as agent-reported outcome figures with their caveat, or as amounts the user typed, labeled as such.

## Intake behavior

New intake accepts narrative or files, sends an idempotent auto-start request, and starts document reading automatically. Optional amounts and owner confirmation of machine transcription do not block starting. Direct activation readiness takes precedence over legacy crew access. Redundant status labels and the old permission-writing prompt stay out. The production build keeps its bundle-size warning and the note that the dynamically imported services module is also statically imported.

The case page is a full-window conversation (see **Case page** above). The top-level discrepancy strip is removed; supplied bill and EOB amounts remain in case details. Version-2 questions appear once in the conversation; earlier authorities keep their original inline reply and provider approval paths. ## Phone-first entry

Phone is the primary entry; email is the fallback for older accounts. `src/Landing.tsx` uses the large wordmark, hero spacing, animated **Open a case** link to `#workspace`, and three-step copy. Phone sign-in lives on the signed-out workspace route through `src/main.tsx` and `src/PhoneEntry.tsx`. `src/PhoneSignIn.tsx` displays **Verify and call me**, explains the verification text, AI onboarding call, and standard case-handling scope, and uses the existing Twilio Verify phone authentication endpoints. Successful verification creates or reuses the phone account. No email is required. Phone OTP readiness and call readiness are separate: `GET /status` must return `onboardingEnabled:true` before the UI offers **Verify and call me** or requests an onboarding call. A missing or false field keeps OTP login available with **Text me a sign-in code** / **Verify and open dashboard** and an explicit call-unavailable message. Linking an existing account and fictional test accounts never request onboarding calls, including fictional numbers typed into the normal form. No case-handling scope is implied by a login-only verification. A separate button retains access to older email accounts without migrating their cases.

`src/phone-onboarding.tsx` requests `POST /phone/onboarding` only after the explicit successful verification action, with `{request_call:true,accept_standard_handling:true}` and the verified session bearer token. It supplies no caller-selected destination. The server owns permanent call idempotency. Mounting, reload, and status polling never submit another call. A failed or uncertain call request retains the login and displays the recorded status; it is not automatically retried. `GET /phone/onboarding` refreshes the dashboard status every ten seconds and can return a case link and onboarding transcript. Unknown receipts remain unconfirmed. The onboarding notice exposes **Stop onboarding and case work** for an existing attempt, including a case already created from it. It calls authenticated `POST /phone/onboarding/stop`, disables the control while pending, and updates to `cancelled` only from the server response. It makes clear that an already requested call may still connect. Failed stops leave a retryable control and never claim success; stale status reads cannot overwrite the stop result. The phone session cache and transient-error recovery in `src/phone-session.ts` remain intact. Session storage keeps the account logged in across reloads within the browser tab. The dashboard retains owner-scoped case listing, conversation, upload, agent controls, and outcomes. Phone users do not get email-verification prompts or Gmail setup. ### Email lead entry

`src/EmailLeads.tsx` lists messages sent to the firm whose sender matches the signed-in account's verified email. The case API checks the managed `neon_auth.user.emailVerified` value by authenticated owner ID; it does not trust email text in a request or an unverified JWT claim. Unverified accounts see a verification action delivered by AgentMail. The server reserves a hashed, owner-bound challenge before sending, expires it after 30 minutes, and records a proof only after the signed-in owner opens the matching link. It never stores the raw token. Pending or uncertain sends are not automatically repeated. The browser removes the token from the URL before confirmation. Existing managed password sign-in remains; the app does not invoke Neon verification mail.

`GET /firm/contact` is public and exposes only a valid configured `AGENTMAIL_PUBLIC_EMAIL`. `GET /email/leads` and `POST /email/leads/:id/claim` require authentication. Claiming requires a workplace-injury or health-insurance selection so an emailed situation is not silently assigned the wrong claims process. Existing claimed messages reopen their case. The workspace presents matching messages without requiring a secret link; `?claim_lead=<id>#workspace` may direct a person to the same workspace. Public-inbox attachments are queued for import when the owner claims the lead; see [AgentMail ingress](agentmail-ingress.md).

`backend/email-verification.ts` implements authenticated `POST /email/verify` and `POST /email/verify/confirm`. Request uses the account email read from managed auth, an allowed website origin, `AGENTMAIL_API_KEY`, and `AGENTMAIL_PUBLIC_INBOX_ID` (legacy `AGENTMAIL_INBOX_ID` fallback). A send reservation in `advocacy_firm_records` prevents repeat clicks or uncertain responses from sending another message during the challenge lifetime. Confirmation consumes a SHA-256 token lookup and writes an email proof tied to the same current account address; changing that address invalidates the proof. Company tools must exclude these private verification records and must not permit agent-written email proofs. Protocol expiration is an authentication control, not a case-work limit.

`backend/verified-email.ts` accepts either the managed account's verified-email state or this app's matching proof. `scripts/email-verification.test.ts` covers real database writes with a mocked AgentMail provider and successful emailed-case creation. `scripts/email-entry-ui-fixture.ts` also covers React StrictMode: a verification link triggers one confirmation, removes its token from browser history, and loads the resulting lead list.

Successful email confirmation also marks an existing case mailbox's client address verified, within the same database transaction, only when the case belongs to that authenticated owner and the mailbox client address matches the verified email case-insensitively. Another owner's mailbox or a different client address is not upgraded. This lets a later authenticated AgentMail reply wake the correct advocate without trusting an intake address alone. New advocate provisioning prefers the current server-verified account email over an unverified intake contact.

## Product framing

Assurance is presented as a functioning claims advocacy service. Phone sign-in scope notices use the `scope-note` class. The legacy manual outreach API (`POST /cases/:id/actions`) is an explicitly synthetic test path because it requires `synthetic: true`; that restriction does not govern persistent case advocates. Fictional login records and test evidence retain their labels.
