# AgentMail intake and replies

`backend/agentmail-webhook.ts` receives AgentMail events at the firm worker's webhook route. Inbound client email and third-party correspondence use AgentMail; advocates write to the case owner through the website conversation. It creates no Naïve inboxes and sends no SMS.

## Incoming messages

The handler verifies the raw body against the Svix signing secret and timestamp before parsing it. A five-minute timestamp window prevents stale signed requests. The durable `advocacy_agentmail_events` ledger deduplicates the provider's `event_id`, including deliveries through more than one webhook. Reusing an event ID with different contents is rejected. Unknown inboxes are ignored rather than attached to a case.

Public-inbox messages create `advocacy_email_leads`, including original plain text and attachment metadata. They do not sign the sender in or grant access to an existing case. Front desk can inspect private leads and send an agent-written invitation through `sendLeadInvitation`. Each invitation reserves its operation before dispatch; a missing receipt remains uncertain and is never automatically resent. Flagged leads cannot trigger invitations until their identity is established through the website.

The claim page requires a signed-in account with an independently verified matching email address and an explicit workflow choice (workplace injury or health insurance). `claimEmailLead` creates one case under that account and the standard handling scope. It does not infer a workflow or create a new permission grant on retries. The full original email remains in the lead and is added to the case conversation on claim; intake fields contain bounded excerpts. Initial webhook evidence is linked to that case after the claim succeeds.

New cases share the company inbox (`AGENTMAIL_PUBLIC_INBOX_ID`) and no longer get a dedicated inbox at hiring, at the user's direction. This ignores per-case mail separation, and the AgentMail plan allows only 3 inboxes. A message in the shared inbox goes to a case when its thread or message ID matches that case's email action in that inbox; it arrives as untrusted case evidence and creates no lead. Any other message there remains a lead. Older cases keep existing mappings. `advocacy_case_mailboxes` binds one AgentMail inbox to one case. `ensureCaseInbox` uses a stable provider client ID and stores both the inbox identifier and its actual email address. Messages from the verified client's address become owner instructions only when sender-domain authentication aligns, the case mailbox is an explicit recipient, and the message is not flagged. Long owner emails are saved as a single durable web conversation message through an internal verified-email path; the public web message API retains its input limit. A verified owner’s attachment-only email queues an owner event and may resume the same parked authority without inventing message text; unresolved dispatches and stopped permission remain protected. Other messages remain third-party evidence; they cannot reactivate owner permission. Thread replies pass through the existing sender, reference, authentication, and evidence checks in `providers/replies.ts` and `reply-service.ts`. Bounce and rejection events wake the case and update a matching action's delivery status without resending it.

Email attachments enter durable `firmRecords` jobs through `backend/email-attachments.ts`. Public-inbox attachments are queued after the owner claims the lead; case-inbox attachments are queued immediately, with flagged messages held. `pollEmailAttachments(pool)` retrieves metadata through AgentMail’s canonical authenticated attachment endpoint and downloads only the returned public HTTPS URL, pins the validated DNS address, rejects redirects, and enforces the existing 5 MB file protocol. It validates file signatures, stores a byte hash and deterministic document ID, uploads to the case document bucket, and wakes the advocate. The existing extraction route runs automatically; a transcription stays unconfirmed. Failures become explicit held records and case events; the original email remains available. No signed download URLs are persisted. Held jobs need reconciliation before another attempt. The firm Function therefore requires document storage credentials and the configured reader variables in addition to AgentMail configuration. When a webhook advertises a body URL instead of inline text, the handler retrieves the message through the canonical AgentMail API, validates its inbox and message IDs, and retains the text. It never follows the supplied body URL. Missing bodies or failed retrieval cause a retryable error rather than pretending that the email was read. Responses have a request-level size limit. A held attachment must not be described as reviewed.

## Configuration and operations

Server-only variables are `AGENTMAIL_API_KEY`, `AGENTMAIL_WEBHOOK_SECRET`, `AGENTMAIL_WEBHOOK_ID`, and `AGENTMAIL_WEBHOOK_URL`. `AGENTMAIL_PUBLIC_INBOX_ID` selects the public intake inbox, falling back to the existing `AGENTMAIL_INBOX_ID`; `AGENTMAIL_PUBLIC_EMAIL` is the separately verified public address shown on the website. Never substitute an opaque inbox identifier for an email address.

Run `npx tsx scripts/configure-agentmail-webhook.ts` for a read-only plan. With `--apply`, the script creates or updates the Assurance webhook, saves its secret privately in `.env.local`, and sends no email. It subscribes to `message.received`, `message.received.spam`, `message.received.unauthenticated`, `message.bounced`, and `message.rejected`. The API key must have the relevant label permissions; a rejected subscription is an error, not a reason to silently omit flagged messages. The subscription covers account inboxes; application routing accepts only the configured public inbox and registered case inboxes.

Migration `0027_purple_adam_destine.sql` adds the three ingress tables. Signature tests run with `npx tsx --test scripts/agentmail-signature.test.ts`. Database integration tests run serially with `OUTREACH_TEST_DATABASE_URL` pointing to a disposable database: `npx tsx --test --test-concurrency=1 scripts/agentmail-ingress.test.ts`. They use fake send providers and fictional addresses.

## Provider references

The implementation follows AgentMail's [Svix verification](https://docs.agentmail.to/webhook-verification), [webhook creation](https://docs.agentmail.to/api-reference/webhooks/create), [inbox creation](https://docs.agentmail.to/api-reference/inboxes/create), [attachment retrieval](https://docs.agentmail.to/api-reference/inboxes/messages/get-attachment), and event schemas for [received](https://docs.agentmail.to/api-reference/webhooks/events/message-received), [bounced](https://docs.agentmail.to/api-reference/webhooks/events/message-bounced), and [rejected](https://docs.agentmail.to/api-reference/webhooks/events/message-rejected) messages. A signed webhook proves its provider origin; it does not independently prove the truth of an insurer's statements.

## Gmail document discovery

Read-only inspection of the current Naïve OpenAPI and connected-app catalog confirmed `gmail` supports `managed_oauth` and `oauth`. The documented setup sequence is `POST /v1/connections/auth_configs` with connector, scopes, and tools, then `POST /v1/connections` with the auth configuration and the case identity. A connection requires the provider's `billing:write` API scope. The catalog includes read tools for finding messages and attachments, but its default tools also include sending and deleting mail. Assurance therefore selects read-only tools and keeps AgentMail as its outbound channel.

Attachment tests run with `npx tsx --test --test-concurrency=1 scripts/email-attachments.test.ts` on the disposable database. Four tests passed with fake provider downloads, storage, and extraction: byte-hashed one-time storage; private URL rejection; stored-file preservation when extraction fails; and flagged attachment holds. No actual participant attachment was downloaded.

## Optional Gmail discovery

`backend/gmail-connection.ts` and `src/GmailConnection.tsx` add a read-only Gmail connection in the case's Documents section. It is optional: email attachments and website uploads continue to work without it. The owner chooses Connect Gmail, follows the provider authorization link, and returns to check its status. The application reports a connection only after Naïve returns `active`; clicking a link is not proof of access. An owner can disconnect or cancel a pending link from the same panel.

Authenticated `/cases/:id/gmail` supports GET status, POST `{connect:true}`, and DELETE disconnect. The server resolves the case's existing advocate identity and rejects cross-owner access, identities reused across cases, stopped cases initiating connections, and provider responses with mismatched bindings. It verifies the configured OAuth scope and allowed tools on every operation. A reserved creation without a confirmed response is reconciled by listing that identity's connections; it is not blindly recreated. Active connections wake that case's advocate and may resume its existing parked authority; stop controls and unresolved-dispatch checks remain in force. Gmail contents remain untrusted evidence; all outgoing emails still use AgentMail.

`NAIVE_GMAIL_AUTH_CONFIG_ID` belongs on the cases Function. Gmail connect/disconnect requires the server-only `NAIVE_SETUP_API_KEY` with the provider’s `billing:write` scope; the implementation falls back to the runtime key only if no setup key is configured. The key is never returned to the client or passed into model context. `scripts/configure-gmail-readonly.ts` defaults to a read-only plan; `--apply` reuses or creates a managed OAuth configuration with only `gmail.readonly` and six read tools, then saves the configuration ID privately. It creates no customer connection and sends no email. The same server-only setup key may be used by the authenticated owner connection API; that API resolves the permitted case identity itself and never accepts an arbitrary identity or auth configuration from the browser. The UI stays hidden until configuration and the case advocate are ready, and it is not shown to phone-session owners.

The SDK defines connection responses with `id`, `identity_id`, `auth_config_id`, `connector`, `status`, `connect_link`, and `connect_link_expires_at`. Returned link hosts are validated before display. Google documents [`gmail.readonly`](https://developers.google.com/workspace/gmail/api/auth/scopes) as viewing messages and settings; this implementation requests no Gmail write scope.

`case_get` includes the case mailbox's actual address and verified customer-address metadata, attachment job status, the website URL, and company playbook content/source projections. It never returns another case's attachment records or arbitrary firm operation records. Playbook authors remain responsible for excluding private client information from reusable content.

Gmail tests: `npx tsx --test --test-concurrency=1 scripts/gmail-connection.test.ts` against the disposable database. Three tests passed with a fake OAuth provider; they do not establish a completed live Google consent flow.

## Runtime credential scope

The original onboarding key was restricted to message read/send in one inbox. A live inbox-read check returned HTTP 403 with `missing_permission`. The user then authorized a new scoped key for inbox read/create, message read/send/reply, spam and unauthenticated-label reads, and webhook read/create/update. It was created in the signed-in console and stored privately; inbox read succeeded. The first new key incorrectly saved webhook Delete instead of Read; API verification exposed this before deployment. With explicit user approval it was revoked, and a replacement was created and its full saved permission list verified. The replacement has no billing, deletion, key-management or unrelated access. The original onboarding key was preserved. This verifies provider access, not webhook delivery or customer mail processing.

### Native Gmail tool execution

The current [Naïve connections documentation](https://usenaive.ai/docs/identity/connections) states that connected-account tools are offered on the next agent turn and governed under `<connector>.<tool>` policy names. `backend/providers/case-agent.ts` permits only the six `gmail.GMAIL_*` read operations from `backend/gmail-policy.ts`; its denied default and the provider's pinned read-only auth configuration exclude Gmail sends, changes, and deletion. No standalone connected-tool execution endpoint exists in the inspected live OpenAPI or installed managed-agent SDK, so Assurance uses this native path rather than an invented proxy endpoint. Previously pinned sessions retain their old tool configuration; new case provisioning receives this policy.

Connection refresh uses `GET /v1/connections/{id}`, which reconciles provider status. The create-only Connect Link is retained in the protected case connection record until expiry because later reads may omit it. It is exposed only through the authenticated owner route, never through case-tool or company-summary projections. Seven regression tests passed: three Gmail database tests (including link retention) and four agent-configuration tests (including the exact read-only tool surface).

## Hosted verification without email delivery

`npx tsx scripts/hosted-firm-webhook-check.ts` loads private configuration and verifies the deployed public firm address, private API authentication, role-token and browser-origin boundaries, schedule authentication, and webhook signatures. It submits only a clearly fictional event for a randomly generated unmapped inbox, first with a bad signature and then twice with a valid locally generated signature. It checks the inbox is unmapped before submission and verifies no event, lead, or outreach row was created. It also reads the actual AgentMail webhook registration to verify the URL, enabled state, and all five required subscriptions. The script never sends email or creates a mailbox, customer, or case. Its sanitized report is saved under ignored `test-results/`.

On November 8, 2026 at 08:20:47 UTC, all these hosted checks passed. The private case/email routes and unauthenticated company MCP returned 401, browser-origin MCP returned 403, and an unsigned schedule request returned 401. The bad webhook signature returned 401; both signed unmapped requests returned 200 with `ignored:true`. Database readback showed zero matching event rows, zero leads, and no change in outreach count. The provider registration matched the configured deployment.

This verifies hosted signature processing and safe rejection/ignore behavior, not actual provider-originated delivery or mapped-event deduplication. The current [AgentMail API index](https://docs.agentmail.to/llms.txt) lists webhook management and event definitions but no test-delivery or replay API. The [official webhook overview](https://docs.agentmail.to/webhooks-overview) describes provider delivery when a real event occurs. No undocumented endpoint was guessed and no email was sent to manufacture that proof.
