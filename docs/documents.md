# Private case documents

`src/Documents.tsx` uploads insurance cards, medical bills, explanations of benefits, and incident records. `backend/document-routes.ts` implements authenticated upload, listing, and download. `backend/document-storage.ts` uses Files SDK's Neon adapter with the branch-injected AWS environment variables. The `case-documents` bucket in `neon.ts` is private; credentials and object keys are not returned to the browser.

Uploads accept PNG, JPEG, WebP, and PDF, up to 5 MB each and 20 documents per case. The backend checks the declared type against file signatures. Downloads are attachments with `nosniff`, behind the same case-owner authorization as the metadata. Automated tests and public examples use fictional files only.

Migration 0005 adds `advocacy_documents`. A client-generated UUID reserves the case, immutable object key, original filename, type, byte count, SHA-256, and document kind before storage writes. A retry must match the reserved case, hash, type, and kind. Concurrent retries write identical bytes. Transitioning from uploading to ready advances the case revision exactly once and clears the previous analysis. A previous review or outreach draft remains historical and cannot authorize work on the new revision.

An interrupted upload remains reserved and can be retried with the same request ID. The current browser retains that ID while the form is open; after a reload, a new attempt reserves a new document. Document retention blocks case deletion.

Saving a file does not mean an agent has read it. The extraction flow below provides reading and an optional owner confirmation. The Naïve intake configuration enables `view_image` access at intake version 6, with per-agent version pins so the other specialists stay at version 5. The standalone proof is `scripts/card-reader-smoke.ts`; case integration is described below. `NAIVE_FILES_API_KEY` is a separate, locally stored key with only file read/write scopes; it is supplied only to the case Function, never the browser.

Verification: `npm run build`; `npx tsx --test scripts/document-storage.test.ts`; `npx tsx scripts/document-app-smoke.ts` verifies actual storage through the deployed authenticated API, UI upload, persistence, immutable concurrent retries, exactly one revision increment, anonymous bucket rejection, and second-user isolation. It creates retained synthetic test records.

## Document extraction and confirmed evidence

Migration 0006 adds `advocacy_document_extractions`, one durable attempt per document. `backend/document-extraction-routes.ts` provides POST extraction start, refresh, and confirmation endpoints under the owner-checked document route. Starting the legacy Naïve reader requires a configured test operator; the hosted direct reader below does not. Refreshing and confirming requires case ownership. Naïve credentials remain server-only (`NAIVE_FILES_API_KEY`, `NAIVE_INTAKE_ID`, and the existing runtime key).

The server verifies the stored file hash before processing. Images are copied to Naïve Files and read through the intake agent's `view_image` tool. A result is accepted only after the session ends, the schema validates, no approvals are pending, and the event log proves a successful view of that exact file. PDF documents use the embedded text layer through `unpdf`, with a 20-page and 30,000-character limit. Image-only PDFs are rejected with instructions to upload page images; PDF text extraction is not OCR and can miss handwriting or image content.

The provider upload is reserved before it begins. An uncertain upload is never repeated automatically; an operator must reconcile it. If a process stops during preparation, its reserved state remains visible rather than silently starting another upload. Once the file ID or PDF text is saved, session creation uses the document UUID as its idempotency key. Reader calls retain the approved $0.25 per-task cap and the intake agent's existing monthly cap.

The UI presents the transcription, named fields, and uncertainty notes. Missing fields are null. On this legacy reader, reading alone does not change claim facts. The owner can compare the transcription with the original and confirm it; confirmation advances the case revision exactly once. Incorrect output remains unconfirmed; a clearer new image or an explicit case-details correction is needed. Confirmation proves the user's review, not insurance coverage.

Crew requests capture case details and document evidence under one case lock. Only confirmed extraction text is included; other files appear as unconfirmed manifests. Structured reviews must reference an exact supplied document UUID and SHA-256. Historical runs keep their immutable input. The model may still misinterpret evidence; neither extraction nor a valid reference establishes eligibility, savings, or an insurer decision.

`src/Documents.tsx` provides read, refresh, and confirm actions. `scripts/document-reader.test.ts` checks image-read provenance, nullable fields, source-reference rejection, and actual PDF text extraction. Live integration verification is recorded separately in the change log. Reading does not send messages or submit claims.

`npx tsx scripts/document-reader-app-smoke.ts` verifies actual image and PDF reads through the deployed API, concurrent/idempotent starts, user confirmation, source-linked crew completion, and null unknown financial values. It requires the existing synthetic test operator to be temporarily enabled. `npx tsx scripts/document-reader-readback.ts` then verifies saved source links and restored spending denials after the allowlist is reverted. Provider pauses remain visible as reader error codes on the retained session; they do not create another paid run.

## Hosted direct reader

When `ASSURANCE_DOCUMENT_READER=direct_openai`, the owner-checked extraction start route uses `backend/providers/direct-document-reader.ts` instead of creating a Naïve session. The cases Function needs server-only `OPENAI_API_KEY`; `ASSURANCE_DIRECT_MODEL` defaults to `gpt-5.4-mini`. The browser never receives these credentials. This path does not require the legacy test-operator allowlist. Existing Naïve attempts remain readable and are not silently transferred.

The server checks the stored file hash, sends the exact image bytes inline to OpenAI, or extracts the bounded PDF text layer, and requires a complete schema-valid transcription. Refusals, incomplete responses, invalid output, and provider errors add no evidence. Image-only PDFs still require page images. Until the owner confirms it, the agent sees the result marked `machine_extracted_unverified`. This is an extraction aid, not a coverage determination or a claim of healthcare compliance.

A unique `direct_openai:<uuid>` attempt fences each database update. Concurrent starts return the current attempt. Failed inference can be retried; a process interrupted for more than two minutes can be replaced, and a late response from its old attempt cannot overwrite the replacement. Retrying inference has no communication or claim-submission effects. `direct_running` and `direct_failed` are visible in the document UI; the Read action can retry either state, with the server enforcing the stale-attempt window. These states use the existing extraction table without a migration.

The document Read control is available independently of the legacy crew-review setting. The backend still checks owner identity and reader configuration. The direct reader is synchronous, with a 60-second model timeout; a failed read leaves the uploaded file available and never confirms the transcription automatically.

Verification: `npx tsx --test scripts/direct-document-reader.test.ts scripts/public-source.test.ts scripts/document-reader.test.ts` passed 12 tests, covering exact image input, complete structured output, rejection of refusals/partial results/429, PDF limits and image-only rejection, and source retrieval protections. The disposable-database route suite (`scripts/direct-document-routes.test.ts`) passed three tests for concurrent starts, one-time owner confirmation, stale-attempt fencing, hash mismatch, and retryable 429 failures. A live direct OpenAI read of an in-memory fictional card returned the expected member ID and null unknown claim number. Hosted direct extraction passed in `scripts/hosted-intake-smoke.ts`; see [activation flow](activation-flow.md).

Provider implementation follows the official [image input](https://developers.openai.com/api/docs/guides/images-vision) and [structured output](https://developers.openai.com/api/docs/guides/structured-outputs) APIs.

## Submission-first document handling

The workspace starts extraction after an upload, including files submitted with a new case. Direct extraction completion atomically saves the reading, advances case revision, and queues a `document_extracted` event. An owner-triggered extraction can resume a human-required historical direct run through the same guarded resume service; a revoked grant, live lease, or uncertain dispatch is not bypassed.

Both the current Naïve advocate and the historical direct agent can read completed transcriptions marked `machine_extracted_unverified` until the owner optionally confirms them. They can organize and pursue information using those readings without requiring a transcription checkbox for every upload. They must preserve uncertainty and ask about conflicts/unreadable fields. Confirmation remains a separate provenance event. `backend/case-outcome.ts` accepts outcome quotes only from ready, owner-confirmed document transcriptions or accepted replies; it checks exact quote presence, not amount arithmetic or whether the quoted text supports the reported decision. Legacy decision paths retain confirmed-document requirements. File hashes and case ownership continue to bind source references.
