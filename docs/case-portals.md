# Case-isolated native browser portals

Current integration direction: the case advocate must use Naïve’s built-in browser tool. The custom `portalAction` proxy is an unexposed prototype, not the selected runtime tool. Reuse its owner credential/context handling and durable reservation/receipt logic when the native tool contract is verified. No custom portal MCP tool has been registered.

`backend/case-portal.ts` proxies the verified Naïve computer/browser API. Each case gets its own computer, named context, existing advocate identity and exact advocate context grant. A new authority must explicitly contain the standard portal handling scope; older read-only or zero-contact grants are not expanded. The browser is restricted to the selected HTTPS hostname. This does not establish an insurer's permission to access its site.

The module exports `portalOpen`, `portalAction`, `portalStatus`, `portalReconcile`, `portalOwnerConnect` and `portalOwnerReady`. Agent calls carry the existing case-tool identity. Owner connect accepts credentials only on a private owner-authenticated route, forwards them to Naïve's identity credential store, and never saves them in case records or model messages. The returned live-view capability is for the owner only, allowing security challenges and personal attestations. Owner-ready saves context and grants only the case advocate access. HTTP routes and MCP integration must preserve these boundaries.

Actions currently include native navigation, typing, clicking, observation and extraction. Each action reserves a case-bound operation and fingerprint before dispatch. Unknown results remain uncertain and block subsequent operations, including a new operation ID. Reconciliation extracts the current page without submitting or clicking and never clears uncertainty automatically. A browser receipt is evidence of what the browser reported, not independently verified claim acceptance or money saved. Revocation is checked immediately before dispatch; an already dispatched action may finish.

The current live OpenAPI at https://api.vetta.sh/v1/openapi.json exposes computers, browser actions, identity credentials, saved contexts and context grants. It does not expose a file-upload browser action. Filesystem write exists, but no verified connection from that filesystem to a browser file input has yet been established. Document upload therefore remains incomplete. The separate documentation hosts failed certificate/TLS checks during this implementation; no API was invented to cover the gap.

`scripts/fixtures/fictional-claim-portal.ts` supplies a local Hono form and confirmation page for a controlled fictional journey. It is not an insurer, sends no external communications and reports no real outcome. It must be hosted at an explicit test HTTPS endpoint for a native remote browser test. No native browser live run or real insurer submission has been performed by this implementation.

Run `npx tsx --test scripts/case-portal.test.ts` for schema/destination checks. Run `scripts/case-portal-db.test.ts` serially against a disposable `OUTREACH_TEST_DATABASE_URL` for identity, scope, credential handling, idempotency, uncertainty and revocation checks. Mocked tests do not establish native provider execution or hosted owner-connect readiness.

The live agent schema accepts arbitrary tool configuration maps and does not document the built-in browser tool name, arguments or configuration. `GET /v1/agents/{id}/computer` exists, but no agent-computer attachment write route was found. Harness discovery confirms native injected tools and approvals without enumerating browser tools. Native tool confirmation must use an observed or documented exact tool contract; the existing case approval whitelist remains unchanged.
